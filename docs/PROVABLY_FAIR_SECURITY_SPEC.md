# HIREE — Secure & Provably Fair Lottery Winner Selection Engine

## Cryptographic Architecture, Security Assessment, and Protocol Specification

**Specification Version**: 1.0  
**Algorithm Identifier**: `HIREE-VRF-v1.0`  
**Classification**: Enterprise-Grade Security Architecture  
**Scope**: Lottery Winner Selection and Draw Integrity exclusively (No financial payouts or wallet custody).

---

## 1. Executive Summary & Security Assessment

The HIREE winner-selection system is engineered to satisfy the highest standard of mathematical fairness, transparency, and tamper-resistance. Neither ordinary participants, campaign administrators, system operators, nor external attackers can predetermine, influence, or manipulate the outcome of any lottery draw.

### Security Assessment Findings of Previous Implementations
1. **Single-Step Randomness Risk**: Selecting winners via single-step `crypto.randomInt` without a public pre-draw commitment allows an insider to secretly run multiple draws and choose a seed favoring a specific ticket.
2. **Snapshot Mutation Risk**: Without a cryptographically frozen eligible ticket snapshot, administrators could silently inject or reassign tickets after a campaign closes.
3. **Modulo Bias Risk**: Simple modulo arithmetic (`entropy % candidateCount`) introduces modulo bias when $2^{256}$ or $2^{32}$ is not cleanly divisible by $N$.
4. **Transparency Deficit**: Verification required authenticated admin access rather than open, client-side zero-trust verification.

### Mitigations Implemented in HIREE-VRF-v1.0
- **Two-Phase Commitment & Reveal Protocol**: The server commits to a 256-bit secret seed **before** the public client/beacon entropy is locked.
- **Deterministic Canonical Snapshot**: Eligible tickets are sorted numerically and serialized into a canonical representation before computing a SHA-256 snapshot hash.
- **Unbiased Rejection Sampling**: Entropy chunks are extracted as 32-bit unsigned integers, and values $\ge \lfloor 2^{32} / N \rfloor \times N$ are rejected, mathematically eliminating modulo bias.
- **PostgreSQL Append-Only Immutability**: Database triggers (`prevent_record_mutation()`) prevent `UPDATE` and `DELETE` on finalized draw records and commitments.
- **Client-Side Browser & CLI Verification**: Any participant can reproduce and verify the draw in the Mini App or terminal using public proofs without privileged access.

## 2. Cryptographic Protocol Specification (`HIREE-VRF-v1.0`)

```
   ┌────────────────────────────────────────────────────────┐
   │                  PHASE 1: COMMITMENT                   │
   │  1. Campaign Closes                                    │
   │  2. Freeze strictly CONFIRMED tickets                  │
   │  3. Serialize Canonical Snapshot -> Snapshot Hash      │
   │  4. CSPRNG generates serverSecretSeed (256-bit)        │
   │  5. Compute SHA-256 Commitment                         │
   │  6. Store & Publish DrawCommitment record              │
   └───────────────────────────┬────────────────────────────┘
                               │
                               ▼
   ┌────────────────────────────────────────────────────────┐
   │              PHASE 2: EXECUTION & REVEAL               │
   │  1. Incorporate Public Entropy (Client Seed / Beacon)  │
   │  2. Verify Snapshot Integrity                          │
   │  3. Compute HMAC-SHA256(serverSecretSeed, context)     │
   │  4. Unbiased Rejection Sampling over [0, N)            │
   │  5. Determine Winning Ticket Number                    │
   │  6. Reveal serverSecretSeed and Publish Proof          │
   └───────────────────────────┬────────────────────────────┘
                               │
                               ▼
   ┌────────────────────────────────────────────────────────┐
   │            PHASE 3: INDEPENDENT VERIFICATION           │
   │  1. Check SHA256(serverSecretSeed:lotteryId:snapshot)  │
   │  2. Verify Snapshot SHA-256 hash against ticket list   │
   │  3. Recompute rejection sampling with revealed seed    │
   │  4. Assert winning index matches drawn winner          │
   └────────────────────────────────────────────────────────┘
```

### Mathematical Definitions

1. **Eligible Snapshot Serialization**:
   Given $M$ confirmed tickets sorted ascending by ticket number:
   $$\text{canonical} = \prod_{i=1}^{M} \left( \text{"TICKET:"} \parallel t_i \parallel \text{"|REF:"} \parallel r_i \parallel \text{"|USER:"} \parallel u_i \right)$$
   $$\text{snapshotHash} = \text{SHA-256}(\text{canonical})$$

2. **Commitment**:
   Given a 32-byte cryptographically secure random secret seed generated by Node.js `crypto.randomBytes(32)`:
   $$\text{serverSeedCommitment} = \text{SHA-256}(\text{serverSecretSeed} \parallel \text{":"} \parallel \text{lotteryId} \parallel \text{":"} \parallel \text{snapshotHash})$$

3. **Public Multi-Party Entropy**:
   $$\text{publicEntropy} = \text{SHA-256}\left(\prod_{j} \text{reservationRef}_j \parallel \text{timestamp}_j \right) \quad \text{or External Beacon}$$

4. **Derivation Context**:
   $$\text{context} = \text{snapshotHash} \parallel \text{":"} \parallel \text{publicEntropy} \parallel \text{":"} \parallel \text{prizeIndex}$$

5. **Unbiased Rejection Sampling**:
   For candidate pool size $N$:
   $$\text{limit} = \lfloor 2^{32} / N \rfloor \times N$$
   For each counter $c = 0, 1, 2, \dots$:
   $$\text{digest} = \text{HMAC-SHA256}(\text{serverSecretSeed}, \text{context} \parallel \text{":counter:"} \parallel c)$$
   Extract consecutive 4-byte integers $V$. If $V < \text{limit}$:
   $$\text{winningIndex} = V \pmod N$$
   Otherwise, reject $V$ and continue. This guarantees that every candidate index in $[0, N)$ has equal probability:
   $$P(\text{index} = k) = \frac{1}{N} \quad \forall k \in [0, N)$$

## 3. Threat Modeling & Security Controls

| Threat Scenario | Implemented Defense Mechanism | Test Verification |
| :--- | :--- | :--- |
| **Unauthorized Draw Trigger** | Strict role-based access control requiring `SUPERADMIN` JWT cookie + CSRF header token. Ordinary customers and unauthenticated requests rejected. | Scenario 1 & 2 (401 / 403) |
| **Operator Cherry-Picking** | Operator must publish `serverSeedCommitment` *before* public entropy is finalized. Changing the seed breaks the SHA-256 commitment check. | Scenario 7 |
| **Ineligible Ticket Injection** | Draw query joins exclusively `Reservation.status = 'CONFIRMED'`. Pending, held, and available numbers are excluded. | Scenario 3 |
| **Concurrent Draw Race Condition** | PostgreSQL transaction isolation with row locking on `DrawCommitment` and `Lottery`. Exactly one request executes; parallel requests receive 409 conflict. | Scenario 4 |
| **Double-Draw Manipulation** | Unique composite constraint `@@unique([lotteryId, prizeLabel])` and commitment status transition (`COMMITTED` $\to$ `EXECUTED`). | Scenario 5 & 9 (409) |
| **Database History Tampering** | PostgreSQL trigger `prevent_record_mutation()` on `draws`, `audit_logs`, and `draw_commitments` forbids `UPDATE` and `DELETE`. | Scenario 6 |
| **Snapshot Silent Modification** | Snapshot hash is verified at draw time. Any addition, deletion, or ownership change causes SHA-256 verification to fail. | Scenario 8 |
| **Modulo Bias Exploitation** | 32-bit rejection sampling discards the biased remainder zone $[ \text{limit}, 2^{32} )$. Zero bias across any pool up to 2,000 tickets. | Scenario 15 |
| **XSS / HTML Injection** | Output encoding in React components without `dangerouslySetInnerHTML`. Zod schema input validation. | Scenario 12 |
| **SQL Injection** | Parameterized Prisma queries; strict UUID validation schemas on all route parameters. | Scenario 13 |
| **Telegram initData Spoofing** | HMAC-SHA256 validation using `HMAC-SHA256(botToken, "WebAppData")` with 24-hour expiration enforcement. | Scenario 10 |
| **IDOR Ticket Inspection** | User identity verified via signed JWT claims; `/reservations/:id` verifies ownership before returning records. | Scenario 11 (403) |

## 4. Trust Assumptions & Limitations

1. **Pre-Draw Commitment Integrity**:
   The fairness guarantee assumes that the participant observes or records the `serverSeedCommitment` and `snapshotHash` before the public entropy source (or draw time) is finalized.
2. **Public Entropy Independence**:
   By default, the platform derives public entropy from all confirmed participant payment references and timestamps. For high-stakes grand prizes, an external public beacon (such as a future Bitcoin or Ethereum block hash) can be provided into `publicEntropy`.
3. **Database Append-Only Enforcement**:
   The PostgreSQL `prevent_record_mutation()` trigger enforces immutability at the SQL level. A root database superuser with direct terminal access could theoretically drop the trigger; therefore, production databases must restrict superuser access and route application connections through a restricted application user.

## 5. Independent Verification Tools

### A. Telegram Mini App Browser Verifier
Participants can verify any completed lottery draw in their browser:
1. Open the Mini App and navigate to **My Tickets**.
2. Tap **Verify Draw** on any completed ticket.
3. The modal retrieves the public cryptographic proof and recalculates the SHA-256 commitment, HMAC-SHA256 digests, and rejection sampling locally in the browser using the Web Crypto API.
4. Shows a green badge (`MATHEMATICALLY VERIFIED FAIR`) and enables downloading the complete snapshot JSON.

### B. Standalone CLI Verifier
Auditors, players, or regulators can verify any draw offline or online:

```bash
# Verify against a running HIREE server
npx tsx scripts/verify-draw.ts <drawId> http://localhost:3001

# Verify using an exported snapshot JSON file
npx tsx scripts/verify-draw.ts --file ./hiree-draw-snapshot.json
```

| `NODE_ENV` | Environment identifier | Set to `production` in staging and production. |

## 7. Network Architecture & Service Exposure

- **Public HTTPS Port**: Only the standard HTTPS entrypoint (port 443 / reverse proxy) is exposed.
- **Internal Ports**:
  - PostgreSQL (`5432`): Bound strictly to `localhost` or private container network.
  - Redis (`6379`): Bound strictly to private network.
  - Node.js API (`3001`): Bound to `127.0.0.1` behind reverse proxy.
  - Internal metrics and debug endpoints: Disabled in production.
